[  0s –  20s]  (hook)
  You've written a function that works. But now you need to time how long it runs. So you add timing code inside it. Then another function needs timing too. So you copy and paste. And then a third one. And suddenly you're maintaining the same timing logic in five different places. There's got to be a better way.

[ 20s –  60s]  (before)
  Right now, if you want to add behavior to a function—like timing it, logging it, or checking permissions—you have two choices. One: you edit the function itself and jam the new code in. Two: you wrap the function call in another function every time you use it. Let me show you option two, because it's the pain point. You'd do something like this: instead of calling my_function(), you'd write a wrapper that calls it, checks permissions, then runs the function. Then you do that wrapping everywhere you call it. It works. But it's tedious and error-prone.

[ 60s – 120s]  (concept)
  Here's the insight: a decorator is like a mail room at the entrance of a building. When a package arrives—that's your function—the mail room doesn't open it or change it. Instead, it stamps it, scans it, maybe logs where it's going. Then it hands the package along unchanged. The mail room wraps every package the same way, using the same process, without you having to manage that wrapping yourself every time. In Python, a decorator is a function that takes another function—your package—and wraps it. The wrapper does extra stuff before and after your function runs. Then the decorator hands back the wrapped version. From that point on, when you call your function, you're actually calling the wrapped version. The magic part: you don't rewrite the wrapping logic. You define it once, and reuse it on any function you want.

[120s – 180s]  (example)
  Let's walk through a real scenario. You're writing a web app. Several endpoints need to check that the user is logged in before they run. Instead of writing that check in every endpoint, you write it once in a decorator. Here's how it works. You define a decorator function—let's call it 'require_login'. This decorator takes your endpoint function as an argument. Inside, you create a wrapper function that checks the user's session. If they're logged in, the wrapper calls the original endpoint. If not, it returns an error. The decorator returns this wrapper. Now, above your endpoint function, you write @require_login. That's it. When you call your endpoint, the wrapper runs first. It checks the session. If you're logged in, your code runs. If not, it stops. Now you have five endpoints, and they all get the same permission check with one line—the @ symbol. The logic lives in one place. If you need to change how login checking works, you edit the decorator once, and all five endpoints update automatically.

[180s – 200s]  (recap)
  If you remember one thing from this video, remember this: a decorator lets you wrap a function with extra behavior without editing the function itself. It's like that mail room—the wrapper stamps and processes every package the same way, and your package gets handed back working just like before, but now with extra metadata. You define the wrapping logic once, reuse it everywhere, and change it in one place.

[200s – 208s]  (cta)
